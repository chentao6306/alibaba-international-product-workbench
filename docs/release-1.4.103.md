# 1.4.103 候选版记录

日期：2026-11-10。源码分支 `codex/1.4.103`，继承 [1.4.102](release-1.4.102.md)。包括客户端、本地业务服务、授权后台、官网、测试与构建源码。生产诊断模块有配套升级；客户报告、商品数据、会话、密钥和安装包不进入 Git。

## 规格接收与 SKU 对应

最新客户实际使用 1.4.102。机械商品的来源规格为 `120w`，其来源选项编号是自定义负数；平台原生选项实际显示 `120 W`。字段写入已经成功，但软件只在存在正数来源选项 ID 时记录平台标签，导致后续严格核对 SKU 组合时仍使用原标签而拒绝。

本版读取同一原生规格栏已经接收的完整选项集合，唯一且严格等价才建立来源值到平台标签的对应。已按可靠选项 ID 确认的翻译继续有效。范围包含、不同功率、重复目标标签、多对一以及多余选择仍拒绝；不按 SKU 行顺序配价，不合并或删除 SKU，不修改原始快照和人工编辑值。

规格矩阵不一致现在有独立错误代码及具体原因：矩阵未出现、组合上限、维度冲突、来源组合未匹配、重复来源/目标组合等。诊断带有限量的实时维度、已填写标签和未匹配行索引，避免只剩一句泛化错误。

同份报告中的其他失败包括类目经营权限不足、详情图片未采集到和损坏图片标签，不能归因于上述 SKU 问题。账号权限需要平台授权；现有数据没有图片地址时不得伪造图片或借用其他商品。

## 可靠提速

1. 实际发布进度会同时传入 `message` 和 `verificationState`。此前即使验证状态完全不变也会重写整个商品库并同步磁盘。本版仅让消息与已初始化且未变化的字符串验证状态走内存进度；首次初始化、验证状态变化、暂停/取消、断点、结果和其他更新仍原子落盘。异步引用冲突与外部写入检测保留。
2. `fillChoice` 合并同一时点对控件类型/role/readonly 的读取；原生 SELECT 的选项、multiple 和回滚前选中值由一次快照取得。填写顺序、联动等待、Other 回滚、写入后核对和提交前验证均保留。
3. 不增加同一卖家表单上的多商品并发，不缩短平台处理时限，不跳过供应的可选属性、规格、媒体或最终回执，不对结果未知的保存/提交自动重发。

合成持久化基准：300 个虚构商品、4.94 MB 工作区、30 次进度事件，整库写盘由 30 次降为 0 次，测得耗时 1872.75 ms → 4.23 ms。这只是本地进度处理开销，不能当作整体上架倍数。

两个相同消费电子样本本轮保存草稿分别 125.356 秒、151.512 秒，之前记录为 139.597 秒、188.129 秒。平台响应会波动，小样本观察不能证明所有商品获得同等提速，也不能据此推算全类目成功率。

## 日志与后台

- 每份上传报告最多 60 条失败摘要、5 份详细现场；按目标叶类目、草稿/提交、规则/AI、错误类型选择现场，避免相同报错挤掉不同类目的证据。
- 一次商品尝试有独立编号、分阶段耗时及失败时的时间线。验证码等待与保存草稿单独识别；时间线最多 120 段，截断明确标记。运行日志只记录允许的字段，不记录请求正文、账号密码、Cookie 或密钥。
- 明确列出详细现场因数量、体积、保留期或未采集而缺失；当前商品和原始来源截断分别标记。不是无限保留所有历史失败，也不把摘要冒充完整现场。
- 诊断写入失败不得替换原始发布错误、阻止下一件或影响成功回执持久化。
- 后台仍使用 schemaVersion 1，兼容旧客户端。`diagnostic-schema.js` 和 `diagnostic-evidence.js` 必须配套升级；部署脚本支持隔离验证、双文件备份、失败回滚、健康与匿名访问检查。

2026-11-10 已部署配套后台模块。真实 HTTPS 约 400 KB 报告上传、存储新字段、重复上传幂等、敏感字段清洗及普通客户端不能读取管理报告均通过。合成验收报告随后清理；客户报告和授权数据未修改。Linux 隔离验证已执行，未制造生产故障来测试回滚。

客户排查方式：发生问题后在「设置 → 问题反馈」上传日志，把 LOG 编号、软件版本、失败商品和操作模式交给维护人员；不要反复点击已显示结果待核对的商品。维护人员优先对照 `failureIndex`、详细 `failures`、`timeline`、平台字段和源码快照，区分来源缺失、映射失败、控件拒绝、权限限制与服务/网络错误。
