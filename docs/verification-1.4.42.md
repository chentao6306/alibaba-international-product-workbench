# 1.4.42 跨类目属性处理

## 目标与范围

多客户使用不同类目，单独补充手机或充电器字段名称不能保证通用性。本次调整采集、合并、字段解析、选项填写和提交前读取结果的共用路径。继续使用实际发布页的属性 ID 和控件；没有增加按商品标题猜测未知属性值的规则。

## 修改

- 采集属性合并先检查全部来源的属性 ID。同名但不同 ID 的字段分别保留，无 ID 的歧义文本不再并入第一个字段；处理顺序不会决定所属属性。
- 不同名称或不同来源分区的无 ID 属性保留差异，交由实际字段解析器判断。重新采集补全时也避免把歧义同名字段挂到第一个属性上。
- 绑定实际表单时优先完整名称的唯一匹配，避免宽泛别名导致两个不同属性无法区分。
- 读取表单原生单选、多选、复选框，以及明确的下拉框单选/多选标记和可见选项。统一拆分来源多值，同时保留完整选项里的逗号、括号和数字千位分隔符。
- 除屏幕、电池外，其他字段明确带单位的测量值也可以与包含它的来源区间进行一致性比较。不把纯数字型号当测量值，不合并不同单位，不缩减明确多选字段的选项。
- 同一叶子类目、相同属性 ID、有效期内的历史表单名称可用于补充中英文对应关系；不复用其他类目的映射，不用历史数据覆盖当前必填规则、控件类型或选项。
- 提交前检查已提供来源值的可选属性，发现联动更新后被清空或未保持所选值时停止提交。未提供来源值的普通可选属性不阻止提交。
- 采集属性规则版本升至 5，旧失败记录可走现有重新采集补全流程；不自动覆盖用户编辑或引用模板。

## 验证边界

上述跨类目浏览器测试使用隔离的模拟表单，不是 12 个类目的真实店铺上架记录。本轮没有进行真实草稿保存或直接上架。

若平台既不提供可对应的属性 ID，也无明确的中英文名称关系，仍不能安全猜测属性。不同客户的经营权限、平台实时选项、类目特有图片或物流要求也不能由这些属性测试证明。部署时应先选不同经营类目的少量商品保存草稿并核对，再扩大到批量任务；保留真实缺项、冲突和平台拒绝反馈。
