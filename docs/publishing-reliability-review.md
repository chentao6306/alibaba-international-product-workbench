# 发布稳定性审查（2026-09-19）

## 对标外贸好帮手

用户指定产品为 [外贸好帮手](https://aliwmhbs.com/)。核对了其[官方功能介绍](https://aliwmhbs.com/wmhbs)和[在线帮助](https://aliwmhbs.com/zxbz)。公开说明包括规格属性直接编辑、主图与型号匹配、视频银行、属性/交易/物流批量编辑、店铺搬家、待优化商品处理和重复商品诊断。

这些是可核实的产品功能，不足以证明其内部使用哪种接口、如何重试、支持多少类目或实际成功率。没有把营销页面当作“所有类目 100% 成功”的证据，也没有复制其程序。对本项目的工程判断是：稳定性必须覆盖采集、编辑、升级、任务设置、浏览器填写、平台回执整个流程，不能仅以一份重新采集过的商品调用发布函数作为交付依据。

## 本项目已确认的问题及修订

| 环节 | 核对结果 | 1.4.28 的处理 |
| --- | --- | --- |
| 历史数据升级 | 新字段进入快照投影后，旧快照原始字节未变，归一化哈希却变化；现有 418 件中 417 件被误报 | 同时识别可验证的旧格式和原始快照哈希；新快照单独标记哈希格式；禁止升级时无条件重新生成已有指纹 |
| 属性提交 | 固定等待 180ms 可能早于控件保存；已有一个选项会被当作整项完成 | 等待每个选项实际回读；后续字段重绘后逐项核对全部值；提交前再核对一次 |
| 中英文选项 | 按 ID 选中中文值后，用英文源文字复核会误判 | 仅记录实际按相同属性/选项 ID 点击并回读的显示名称；仍检查当前已选值，不用缓存代替表单核对 |
| 旧采集格式 | 原生多选控件不能识别逗号拼接的旧来源值 | 对多选拆分旧数据；完整选项本来包含逗号时保持原样 |
| 任务销售方式 | 客户旧任务为完整物流，先前实测为询盘；暂停任务不能调整 | 暂停时可改变剩余商品的销售方式；保留任务进度、成功回执及其余设置 |
| 包装与物流依赖 | 填了包装会触发完整物流要求；空包装的商机品可以被接受，形成看似矛盾的结果 | 保留两种明确策略：询盘商品把包装保留在详情；完整物流使用真实包装和运输属性。没有给含电池/液体商品编造“普货” |
| 浏览器窗口 | 最小化窗口可能不能直接最大化；隐藏位置使用了错误 CDP 参数名 | 先恢复再最大化，使用 left/top 移动窗口，异常也释放调试会话 |
| 验证方法 | 旧测试直接调用发布器，并优先使用另一份重新采集的资料 | 新增生产 API 回归工具，从已安装客户端复制指定商品，调用 `/api/publish`，经过补采、任务路由、库存策略、填写和结果持久化 |

## 必须保留的约束

- 采集的原始快照、用户编辑和发布结果保持独立。软件升级不能把工作数据重新认定为原始采集数据。
- 类目与属性按发布页实时结构识别，先匹配属性 ID，再匹配对应语言和别名。不同属性即使名称相似也不能强行合并。
- 图片、规格、价格、必填属性都需要回读；点击成功或输入框里有搜索文字不等于平台已接受。
- 只有平台明确成功反馈才记录成功。提交回执不明确时不能自动重复提交。
- 验证码等待保留进度；数据缺项、账号类目限制、网络/控件异常应保留不同原因，不能统一叫“上架失败”。
- 源站未公开的运输事实不能由无关商品推断。用户明确选取的参考商品可以复用，仍需保留来源和选项核对。

## 回归方法

`tools/publish-workflow-qa.mjs` 必须通过 Electron 运行，以便读取当前 Windows 用户加密保存的卖家会话。输出目录与已安装软件目录隔离，不改动原工作区。默认保存真实草稿，只有显式 `--submit` 才直接发布。运行前已获得账号所有者测试授权。

```powershell
$env:TEMP='D:/CodexBuildTemp'
$env:TMP='D:/CodexBuildTemp'
npx electron tools/publish-workflow-qa.mjs --account=卖家账号 --ids=来源ID1,来源ID2 --output=D:/CodexBuildTemp/工作流测试 --listing-mode=inquiry
```

测试账本包含正式调用参数、逐步进度、实际选中值及成功/失败回执。再次直接提交前检查账本，避免重复发布。真实商品数据、会话、截图和账本仅本地保存，不能提交 Git。

当前审查不等于完成对所有经营类目、所有客户 Windows 环境的认证。版本交付记录需要列明实际测试范围；不能把十个样本的结果外推成全平台成功率。
